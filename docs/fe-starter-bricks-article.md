# Из рабочей сборки в открытый CLI: Fe Starter Bricks для многостраничных сайтов на Twig, Pug или Nunjucks (и письма на MJML)

В рабочих проектах я привык собирать многостраничные сайты и фронтенд-интерфейсы на собственной сборке. Она не была заготовкой, которую берут из прошлого проекта и вычищают: это был один инструмент, который жил и развивался сам. Сначала в нём были шаблоны и SCSS, потом скрипты, оптимизация изображений, спрайты, а позже и email-шаблоны.

Проблемы начались, когда проектам понадобились разные наборы возможностей: где-то Twig, где-то Pug или Nunjucks, где-то TypeScript, а где-то хватало обычного JavaScript. Сборка превращалась в набор условий и исключений.

Тогда я разложил её на общую основу и подключаемые слои и вынес в отдельный CLI. Так появился **Fe Starter Bricks**: он спрашивает четыре вещи (шаблонизатор, JS или TS, нужны ли письма на MJML, имя папки) и собирает проект из общей базы и выбранных слоёв.

В статье расскажу, как это устроено, почему там Gulp и Webpack, а не Vite, и для каких задач инструмент подходит (а для каких нет).

![Выбор шаблонизатора в CLI](https://github.com/evscoder/fe-starter-bricks/raw/master/docs/images/cli.png)

## Быстрый старт

Нужен Node.js `>= 20.12.0`.

```bash
npm create starter-bricks@latest
```

CLI задаёт четыре вопроса:

| Настройка | Варианты | По умолчанию |
| --- | --- | --- |
| Имя папки | Например, `my-new-project` | `my-new-project` |
| Шаблонизатор | Twig, Pug, Nunjucks | Twig |
| Скрипты | TypeScript или JavaScript | TypeScript |
| Email-шаблоны | Добавить MJML или пропустить | Пропустить |

Дальше обычное:

```bash
cd my-new-project
npm install
npm start
```

Сайт откроется на `http://localhost:4200/`, BrowserSync перезагружает страницу при изменении файлов. Генератор работает и через `npx`, `yarn create`, `pnpm create` и `bun create`.

## Как устроена генерация: база и слои

В репозитории шаблоны разложены по назначению:

```text
packages/create-starter-bricks/templates/
├── base/
├── template-twig/
├── template-pug/
├── template-nunjucks/
├── template-js/
├── template-ts/
└── template-mjml/
```

В `base` лежат общая структура и конфигурация сборки, в остальных папках файлы под конкретный выбор. Для Twig + TypeScript + MJML генератор копирует базу, поверх неё слои Twig, TypeScript и MJML, записывает выбранные параметры в `user.config.js` и обновляет имя в `package.json`.

Смысл в том, что общая сборка правится в одном месте, а не в отдельной полной заготовке под каждую комбинацию технологий.

## Почему Gulp и Webpack, а не Vite

Это первый вопрос, который мне зададут, поэтому отвечу сразу.

Сборка выросла из практики. Результат моей работы это набор HTML-страниц, который затем отдаёт бэкенд или подключает CMS. Для такого процесса мне нужны серверные шаблонизаторы с layouts и компонентами, обработка изображений, SVG и спрайтов, а также письма в том же окружении. Gulp 4 и Webpack 5 закрыли эти задачи, и у каждого из них своя зона ответственности: Gulp обрабатывает шаблоны и ресурсы, Webpack собирает скрипты и стили. Переписывать работающую сборку на другой инструмент ради самого факта обновления я не стал.

Для стилей есть SCSS, PostCSS и поддержка Tailwind CSS, для проверки кода ESLint и Stylelint.

Если вы делаете SPA или проект на React/Vue, берите Vite или готовый фреймворк, этот инструмент не для вас. Fe Starter Bricks про другое: заготовка именно под вёрстку для последующей интеграции с бэкендом, где Twig это вариант по умолчанию.

## Для каких проектов это подходит

Корпоративные сайты, многостраничная вёрстка, темы для CMS, Symfony-представления, статическая интеграция фронтенда. Twig выбран по умолчанию из-за PHP- и Symfony-проектов: синтаксис шаблонов будет привычным.

Важно: генератор создаёт **фронтенд-заготовку и локальную сборку**. Интеграция с серверным приложением остаётся отдельной задачей.

## Что внутри сгенерированного проекта

```text
my-new-project/
├── src/
│   ├── assets/          # изображения, SVG, favicon, статика
│   ├── js/ или ts/      # выбранный слой скриптов
│   ├── styles/          # SCSS
│   └── templates/       # страницы, layouts, компоненты
│       └── emails/      # если выбран MJML
├── build/               # результат сборки
├── user.config.js
└── package.json
```

Команды:

```bash
npm start        # сборка, локальный сервер, слежение за файлами
npm run build    # production-сборка в build/
npm run lint     # ESLint по src/ с автоисправлением
```

`npm run lint` запускает ESLint с `--fix`, то есть может изменить исходники, а предупреждения считаются ошибкой.

Основные настройки лежат в `user.config.js`: `templateEngine`, `typeScript`, `emailsBuild`, `folderBuild`, `assetsBuild`, `serverIndexPage`, `optimizeImages`, `spritePng` (PNG-спрайты по умолчанию выключены).

## Письма на MJML рядом с сайтом

Подтверждение регистрации, восстановление пароля, уведомления: письма часто делаются вместе с сайтом, поэтому MJML можно включить сразу. Исходники попадают в `src/templates/emails/`, скомпилированный HTML в `build/emails/`. После `npm start` пример доступен по адресу:

```text
http://localhost:4200/emails/address.html
```

Отправка писем и подключение к почтовому сервису в проект не входят.

## Ограничения

- Изменение `templateEngine` или `typeScript` в `user.config.js` после генерации переключает настройки сборки, но не копирует файлы другого слоя. Технологии нужно выбирать при создании проекта.
- Слои разделены на уровне исходных файлов. Общий `package.json` копируется целиком, поэтому зависимости всех инструментов могут попасть в установку независимо от выбора.
- Сборка из нескольких инструментов требует сопровождения конфигурации и обновлений. Берите её, когда предусмотренные процессы действительно нужны.
- Проверка кроссбраузерности, доступности, производительности и отображения писем в почтовых клиентах остаётся на вас.

## Попробовать

Проект под лицензией MIT: [репозиторий на GitHub](https://github.com/evscoder/fe-starter-bricks), пакет [в npm](https://www.npmjs.com/package/create-starter-bricks).

Проще всего оценить его так: сгенерируйте проект, перенесите одну страницу с общим layout, стилями и небольшим скриптом и посмотрите, насколько удобен цикл разработки. Буду рад issue и звёздам, а ещё больше комментариям о том, каких шаблонизаторов или слоёв не хватает.
